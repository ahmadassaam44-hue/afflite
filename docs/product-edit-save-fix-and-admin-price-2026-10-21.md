# إصلاح «تعذر الحفظ» في تعديل المنتجات + سعر الأدمن = السعر النهائي — 2026-10-21

## المشكلة اللي وصلت من الإدارة

> **«تعذر الحفظ. راجع الاسم والسعر والقسم وروابط الصور.» — ليه بتظهر أثناء التعديل؟**

الرسالة دي بتطلع من `dashboard/admin.php` (حفظ تعديلات المنتج `ov_action=full_details` —
فورم «تعديل كل التفاصيل» في تبويب المنتجات) لما التحقق على السيرفر بيرفض **الحاجة اللي الفورم
نفسه حطها**. يعني الأدمن بيضغط حفظ من غير ما يغلط أي حاجة، والفورم هو اللي بيوقّع نفسه:

### السبب ١ (الشغال دلوقتي): صور التفاصيل المحلية `assets/detail/...`
- الموقع بيخزن نسخ محلية لصور التفاصيل في `assets/detail/`، و`data/detail_index.json`
  فيه **132 منتج vendoor** mapped لمسارات زي `assets/detail/vendoor_1252_00071.jpg`،
  وكمان **146 صورة** من المسارات دي مكتوبة جوه `data/vendoor.json` نفسه.
- `with_detail_imgs()` بيضيف المسارات دي لمصفوفة صور المنتج وقت القراءة، والفورم بيحطها
  في textarea «روابط الصور» سطر سطر.
- التحقق عند الحفظ كان بيقبل بس `^(https?://|/)` — ومسار `assets/...` **ما بيبدأش بـ /**،
  فالسيرفر بيرفض الروابط اللي هو نفسه عرضها ⇒ `return false` ⇒ «تعذر الحفظ» —
  حتى لو التعديل كان في الاسم أو السعر بس.

### السبب ٢ (شغال كمان): روابط صور فيها فاصلة
- `$split_lines` كان بيقسم على `[\r\n,]+` — **الفاصلة كانت فاصل تقسيم**.
- في `data/safqa.json` فيه 5 صور روابط CDN صحيحة اسم الملف فيها فاصلة
  (مثال: `...Rechargeable%20Wireless%20Ceiling%20Fan,%20Portable%20Hanging...`).
  الرابط بيتقص نصين، والتاني مش بيبدأ بـ http ⇒ رفض ⇒ نفس الرسالة.

### أسباب كامنة (كانت هتظهر مع أول حالة):
- **القسم**: الدراوب داون بيضيف قسم المنتج الحالي لو مش من الأقسام الموحدة (`wf_category_canonical`)
  وبيحدده selected — لكن السيرفر كان بيرفض أي قسم غير موحّد. (دلوقتي كل بيانات الأقسام موحدة،
  فكانت كامنة.)
- **صور الخيارات المركبة** (`variants_detailed[].image`): نفس الـ regex الرافض للمسارات المحلية.
- **تعديل الصورة السريع** (`ov_action=image`): نفس الـ regex.

## الإصلاح

### 1) `wf_image_url_allowed()` — قبول المسارات المحلية (config.php)
```php
function wf_image_url_allowed($u) {
    $u = trim((string)$u);
    if ($u === '' || strlen($u) > 600) return false;
    if (preg_match('~^(https?://|/)~i', $u)) return true;
    return strpos($u, 'assets/') === 0;   // صور التفاصيل المحلية
}
```
بتستخدم في التلات مواضع: صور «كل التفاصيل»، صور الخيارات المركبة، وتعديل الصورة السريع.
`data:` و`javascript:` وأي حاجة تانية لسه مرفوضة (أمان زي ما هو). المسار المحلي بيترندر
عبر `asset_url()` زي ما هو، وdedupe في `with_detail_imgs()` بيشتغل لأن الصيغة محفوظة.

### 2) الفاصلة مابقتش فاصل تقسيم للصور
`$split_lines($value, $max, $pattern = '/[\r\n,]+/u')` — الصور بتتقسم **على الأسطر بس**
(`/[\r\n]+/u`)؛ الألوان والمقاسات لسه بتتقسم على الفاصلة كمان زي الأول.

### 3) قسم المنتج الحالي مقبول
قبل الحفظ: `find_product_by_id($raw_id, $plat)` بيجيب القسم الحالي الفعال، والتحقق بقى:
`canonical` **أو** قسم المصدر **أو** القسم الحالي للمنتج — فاللي الفورم بيعرضه selected مايترفضش.

### 4) رسالة الخطأ بتقول السبب بالظبط
بدل الرسالة العمومية، كل رفض بيحدد سببه:
`تعذر الحفظ: رابط صورة غير مقبول: ...` / `القسم غير معروف: ...` / `السعر لازم يكون رقمًا...` /
`الاسم فاضي أو أطول من 200 حرف` / `JSON الخيارات المركبة غير صالح...` — والرسالة القديمة
بقت fallback لو السبب مش محدد.

### 5) سعر الأدمن = السعر النهائي (حماية فلوس — مهمة بعد تخفيض 12%)
- **قبل كده**: الفورم بيحط «سعر العرض» (اللي داخل فيه هامش 2% **وتخفيض 12%** من PR الأخير)،
  والحفظ بيخزنه كـ«سعر مصدر» في override — فتاني قراءة بيتركب عليه الهامش والتخفيض **مرة تانية**:
  كل ضغطة حفظ كانت هتنزل السعر ~12% (900 → ~810 → ~730...). كانت رسالة الخطأ دي بالذات
  هي اللي مانعة الكارثة على منتجات vendoor/safka، وأول ما نصلحها كان لازم نصلح دي معاها.
- **دلوقتي**: `apply_product_override_record()` بيختم الصف بـ `_price_override = true`،
  و`store_price()` بيبدأ بـ:
  ```php
  if (!empty($p['_price_override']) && is_numeric($p['price'] ?? null)) return round(max(0, (float)$p['price']), 2);
  ```
  أي سعر يحدده الأدمن (من «تعديل كل التفاصيل» أو من خانة السعر السريعة) بقى **السعر النهائي
  بالظبط** للعميل والطلبات — من غير هامش ولا خصم فوقه، والحفظ المتكرر **idempotent**
  (تحفظ 900 تفضل 900). المنتجات من غير override لسه بتاخد المسار العادي:
  سعر المصدر → هامش 2% → تخفيض 12% → تقريب 5/0.
- الرقمي كمان: override على منتج g2g/social = سعر نهائي بنفس القاعدة.

## الاختبارات — `tests/ui/manual-country-currency.cjs`

- فيكسترز جديدة: `product_overrides.json` (سعر أدمن لـ t2 وg1) + `g2g.json`.
- 14 assertion جديدة (القسم 14): `wf_image_url_allowed` (https بفاصلة ✓، `/` ✓،
  `assets/detail/...` ✓، ورفض `data:`/`javascript:`/الدومين المجرد/الفارغ)،
  `_price_override` على الصف، `store_price`/`display_price` = 900 بالظبط للمنتج المتعدَّل،
  إعادة حفظ سعر العرض بتفضل 900 (idempotent)، المنتج من غير override لسه 1000→900
  (هامش+خصم)، override الرقمي نهائي (560→600).
- Wiring جديد: استخدام المساعد في ≥3 مواضع، رسالة بسبب محدد، تقسيم الصور على الأسطر فقط،
  قبول القسم الحالي (`find_product_by_id`)، الختم والـ early-return في `store_price`.
- النتيجة: **359 assertion / 0 فشل** (كانت 345) + parse نظيف لـ `config.php` و`admin.php` (php-parser).

## خلاصة للإدارة

الرسالة كانت بتظهر لأن **الفورم بيحط في الصور روابط محلية (assets/detail) وروابط CDN فيها
فاصلة، والتحقق القديم كان بيرفضها** — مش غلط منك في الاسم أو السعر أو القسم. اتصلحت،
وكمان أي رفض مستقبلي هيطلع **بسببه المحدد** في الرسالة. وزودنا حماية: السعر اللي بتحطه
بايدك بقى هو السعر النهائي بالظبط — الحفظ المتكرر مش هيغيره.
