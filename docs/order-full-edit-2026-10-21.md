# التعديل الكامل للطلبات — المسوق والإدارة (بما فيها العمولة) — 2026-10-21

## الطلب

> «خلي المسوق او الاداره يعدل كل التفاصيل بما فيهم العموله وكل حاجه»

قبل كده: المسوق كان بيعدل **بيانات العميل والكمية بس** (مهمة 11)، والإدارة كان عندها تغيير الحالة + ملاحظة + مراجعة إيصالات — **مفيش تعديل للحقول نفسها**.

دلوقتي: **فورم تعديل كامل** للاتنين — كل حقل في الطلب قابل للتعديل، والسيرفر بيحاسب كل حاجة من جديد.

## الحقول القابلة للتعديل

| المجموعة | الحقول | مسوق | إدارة |
|---|---|---|---|
| العميل | الاسم، الموبايل، رقم بديل/واتساب، المحافظة/المنطقة، المدينة/المركز، العنوان، ملاحظات | ✅ | ✅ |
| المنتج | اسم المنتج، المواصفات/العرض، اللون، المقاس | ✅ | ✅ |
| الفلوس | الكمية (1–99)، سعر القطعة، مصاريف الشحن، **العمولة الإضافية على القطعة**، **عمولة المسوق على الطلب كله** | ✅ | ✅ |
| الحالة والمصدر | حالة الطلب (6 حالات)، كود المسوق (تحويل العمولة)، الحملة/المصدر (sub) | ❌ | ✅ |

- **المسوق**: طلباته هو بس (مطابقة كود الإحالة) وحالتها لسه قابلة للتعديل (قيد التأكيد/مؤكد) — نفس بوابات مهمة 11.
- **الإدارة**: أي طلب في أي حالة.
- الرقمي/السوشيال (`g2g`/`social`): العمولة الإضافية **بتتصفر تلقائيًا** — نفس قاعدة الإنشاء.

## قواعد الحساب (سيرفر-سايد بالكامل)

- **الإجمالي** = سعر القطعة × الكمية + الشحن − خصم الكمية (`wf_bulk_discount` بعملة المنتج) — بيتحسب من جديد في كل حفظ.
- **حقل ناقص أو فاضي = سيب القيمة الحالية** — مفيش تصفير بالغلط (التوافق مع أي نداء قديم محفوظ).
- التحقق: كمية 1–99، سعر قطعة ≤ 200000، شحن ≤ 20000، عمولة ≤ 50000، عمولة إضافية ≤ `MAX_MARKUP_AMOUNT` (5000)، موبايل ≥ 10 أرقام، اسم مطلوب. الحالة الغلط أو كود المسوق غير الموجود **بيرفضوا الحفظ كله**.

## تسوية العمولة في المحفظة (من غير ازدواج)

فرق العمولة (Δ = جديد − قديم) بيتسوى بحسب `comm_state`:

| حالة العمولة | زيادة | تخفيض |
|---|---|---|
| `pending` | `commission_credit_pending(Δ)` (معلق) | `commission_reverse(−Δ)` (من المعلق) |
| `confirmed` (مُسلَّم) | معلق + `commission_release(Δ)` (للمتاح) | `commission_reverse(−Δ)` (من المتاح) |
| `reversed` / `suspended` | **مفيش حركة** — الطلب الملغي ميتحركش في المحفظة | |

- **عمولة الفريق (الإحالة)** بتتسوى بنفس نسبة الإنشاء `REF_TEAM_RATE` (4%) خلال 243 يوم — بنفس أسباب الدفتر اللي `team_ledger_for_order` بتجمع بيها، فالأرقام بتفضل متسقة.
- **تغيير الحالة مع التعديل**: دورة حياة كاملة زي معالج الحالة بالظبط (تحرير عند التسليم / سحب عند الإلغاء أو الإرجاع / سحب عند التراجع عن التسليم) + `status_at` + إشعار العميل والمسوق.
- **تحويل الطلب لمسوق تاني (إدارة)**: سحب عمولة القديم (مباشرة + فريقه) بحسب حالتها، ثم `credit_affiliate_amount` للجديد (فريقه بيتسجل تلقائيًا)، ولو الطلب مُسلَّم بتتحرر فورًا. كود مش موجود ⇒ **مفيش حفظ خالص**.
- `comm_state` النهائية دايمًا مشتقة من الحالة + العمولة الفعلية (نفس خريطة معالج الحالة).

## الأودت والإشعارات

- `log_audit('admin_order_full_edit', …)` بكل الحقول اللي اتغيرت (قديم→جديد) + الحالة + `m_earn` + هل الكود اتحوّل.
- تعديل المسوق: `log_audit('marketer_edit', …, changed)` + إشعار للإدارة (موجود من مهمة 11).
- المسوق بياخد إشعار لما الإدارة تعدل/تحوّل طلب على كوده، والمسوق القديم بياخد إشعار سحب عند التحويل.
- ختم على الصف: `mk_edited_at/mk_edited_by` للمسوق، `adm_edited_at/adm_edited_by` للإدارة.

## الواجهات

- **`dashboard/marketer.php` (طلباتي → تعديل)**: الفورم اتوسع لكل الحقول مع تلميحات العملات (سعر القطعة/الشحن بعملة الطلب، العمولات بج.م دايمًا) — الإجمالي بيتعرض بعد الحفظ.
- **`dashboard/admin.php` (الطلبات → «تعديل كامل»)**: زر جديد في كل صف بيفتح فورم كامل فوق الجدول: الحالة select + كود المسوق (مع اسم المسوق الحالي وتحذير إن التغيير بينقل العمولة بفريقها) + sub + كل حقول العميل/المنتج/الفلوس. الفورم القديم السريع لتغيير الحالة فضل شغال زي ما هو.
