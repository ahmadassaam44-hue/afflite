## 2) «تعذر قراءة رد الخادم — الطلب ممكن يكون اتسجل أو لأ» — اتلغت نهائيًا
الرسالة كانت تظهر لما رد السيرفر يوصل للمتصفح غير مقروء (صفحة فحص من الاستضافة، قطع اتصال، أو تأخير). الطلب في الحالات دي **غالبًا بيكون اتسجل فعلًا** — والمشكلة إن الرد اتبوّظ في الطريق.

### سببان عمليان اتعالجوا في السيرفر (dashboard/orders.php + config.php)
1. **إشعارات التليجرام/الواتساب كانت بتتنفذ قبل رد الـ JSON** — أي بطء في cURL كان بيخلي الاستضافة تقطع الطلب وترجع صفحة خطأ بدل الرد. دلوقتي:
   - الإشعارات بتتجمع في طابور (`wf_order_notify_queue`) وبتتنفذ **بعد** ما الرد يتبعت للمتصفح (`wf_order_notify_flush` بعد `Content-Length` + `flush` + `fastcgi_finish_request`/`litespeed_finish_request`).
   - الـ shutdown fallback بينفذ الطابور كمان لو حصل خطأ بعد تسجيل الطلب.
2. **إعادة الإرسال كانت ممكن تكرّر الطلب** — دلوقتي كل محاولة إرسال بتاخد `client_token`:
   - نفس التوكن وصل تاني؟ السيرفر بيرجّع بيانات الطلب الأصلي (`duplicate:true`) من غير ما يسجل طلب جديد.
   - نقطة تأكيد جديدة: `GET dashboard/orders.php?ajax_order_check=1&client_token=…` بترد JSON `{found:true, order_no, …}` أو `{found:false}` (`wf_find_order_by_token`).
   - كمان: إرسال ajax بقى بيتعرف بـ `X-Requested-With` — الفورم الأصلي من غير JS بياخد صفحة HTML نجاح زي زمان بدل JSON خام.

### المتصفح (assets/ui.js) — مفيش رسائل مبهمة تاني
`wfOrderSubmitWithCheck` موحّد للديالوج السريع وفورم صفحة الهبوط:
1. إرسال POST بالتوكن.
2. الرد مقروء و`ok` → نجاح ✅ (زي الأول).
3. الرد **مش مقروء** → «⏳ جاري التأكد إن طلبك اتسجل...» → طلب تأكيد بالتوكن:
   - `found:true` → شاشة النجاح برقم الطلب الحقيقي.
   - `found:false` → **إعادة تلقائية واحدة** بنفس التوكن (آمنة — السيرفر مايكررش).
   - التأكيد نفسه فشل → التوكن يتخزن `_wfPendingOrderToken` وأي ضغطة إرسال جاية بتتأكد منه **الأول** قبل ما تسجل طلب جديد (منع التكرار حتى في أسوأ حالة).
4. رسالة «الطلب ممكن يكون اتسجل أو لأ» و«تعذر قراءة رد الخادم» و«تعذر الاتصال بالخادم» **اتشالوا كلهم**.
